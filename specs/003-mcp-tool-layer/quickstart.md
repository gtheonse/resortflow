# Quickstart: MCP Tool Layer

**Feature**: `003-mcp-tool-layer` | Validates this feature end-to-end once implemented.
References `contracts/` and `data-model.md` rather than repeating them.

## Prerequisites

- Phase 1's five simulators running and seeded: `make up && make seed` (or
  `docker compose --profile sims up -d` per the Phase 1 handoff).
- This feature's schema amendment (`contracts/tool-error-envelope-amendment.md`) is already
  applied to `docs/contracts/schemas/tool-error.schema.json` (ADR-015, Accepted) — nothing
  further to do here.
- `MCP_DEV_SIGNING_KEY` set (generated by `make seed` if absent, per
  `contracts/caller-identity-contract.md`).

## Bring up the gateway

```bash
docker compose --profile app up -d mcp-gateway
```

Five domain servers should now be reachable behind one process on `:9100`
(`/dining`, `/entertainment`, `/stay`, `/wellness`, `/gaming` — exact mount paths are an
implementation detail of `mcp/gateway/main.py`, not a frozen contract).

## Scenario 1 — the registry is honest (SC-001, SC-002)

The **gating** proof is in-toolchain, since `make eval` is this project's CI gate and Node is
not part of it:

```bash
pytest mcp/tests/contract/test_registry_schemas.py -q   # MCP client, five mount paths
```

The inspector is the same proof for a human, and is how to eyeball a schema interactively:

```bash
npx @modelcontextprotocol/inspector http://localhost:9100/dining
```

Expected either way: 8 tools listed, each with a valid, complete input/output schema. Repeat
for the other four mount paths; expected counts per `contracts/tool-registry.md` (7, 7, 6, 3).
Confirm `/gaming` lists exactly 3 tools, all named `check_*`/`get_*`/`list_*`, and that
searching all five listings for any `create_*`/`confirm_*`/`cancel_*` name under `gaming`
returns nothing (SC-011).

## Scenario 2 — tenant crossing is impossible (SC-003, SC-004)

```bash
# Mint two tokens for different tenants (contracts/caller-identity-contract.md)
TOKEN_MGV=$(python -m gateway._shared.identity issue --tenant MGV --scopes dining:read,dining:hold,stay:read,stay:hold)
TOKEN_MHB=$(python -m gateway._shared.identity issue --tenant MHB --scopes dining:read)

# 1. Normal call succeeds against the caller's own tenant
curl -s -H "Authorization: Bearer $TOKEN_MGV" ... resortflow.dining.list_venues   # → MGV venues only

# 2. Explicit cross-tenant argument is refused outright, not silently ignored
curl -s -H "Authorization: Bearer $TOKEN_MGV" ... resortflow.dining.check_availability \
     -d '{"tenant_id": "MHB", ...}'                                        # → refused (FR-009)

# 3. A resource id known to belong to the other tenant is refused / not-found
curl -s -H "Authorization: Bearer $TOKEN_MHB" ... resortflow.stay.get_stay_details \
     -d '{"stay_id": "<a stay_id seeded under MGV>"}'                      # → refused / not-found

# 4. No token, expired token, tampered signature
curl -s ... resortflow.dining.list_venues                                        # → refused, no dispatch
```

Expected across an adversarial pass covering both tenants × all five domains: zero
cross-tenant reads or writes succeed, zero other-tenant values appear in any response or
failure detail (SC-003), 100% of missing/expired/unverifiable-credential calls refused before
any upstream call (SC-004).

## Scenario 3 — entitlement boundary holds (SC-005)

```bash
TOKEN_READONLY=$(python -m gateway._shared.identity issue --tenant MGV --scopes dining:read)
TOKEN_UP_TO_HOLD=$(python -m gateway._shared.identity issue --tenant MGV --scopes dining:read,dining:hold)

# read-only caller: read succeeds, hold refused
resortflow.dining.check_availability   # succeeds with TOKEN_READONLY
resortflow.dining.hold_table           # refused with TOKEN_READONLY, succeeds with TOKEN_UP_TO_HOLD

# read+hold caller still cannot commit
resortflow.dining.confirm_reservation  # refused with TOKEN_UP_TO_HOLD — holding hold never implies commit
```

## Scenario 4 — every failure is one of four classes (SC-006, SC-007, SC-016)

Drive each simulator's `X-Sim-Fault` header (Phase 1's `sim-control-plane.md`) through every
supported mode, plus the two new response-validation cases this feature adds:

| Forced condition | Expected `error_class` |
|---|---|
| `X-Sim-Fault: error_500` | `RETRYABLE` |
| Any simulator-supported fault mode | exactly one of the four classes, never unclassified |
| Unparseable 2xx body (`schema_drift` fault mode, once added per research.md's cross-track note) | `RETRYABLE` (FR-034) |
| Schema-invalid-but-parseable 2xx body | `TERMINAL` (FR-035), zero fields passed through (FR-036) |

Confirm no response ever contains a vendor's own envelope shape (`{"error": {...}}`,
`{"fault": {...}}`, or the flat/legacy shape) — only the normalized envelope.

## Scenario 5 — retries are safe (SC-008, SC-009)

```bash
# Same idempotency_key, sent twice
resortflow.dining.confirm_reservation -d '{"idempotency_key": "resortflow:sess1:hold1:1", ...}'
resortflow.dining.confirm_reservation -d '{"idempotency_key": "resortflow:sess1:hold1:1", ...}'  # identical outcome, no second booking

# Missing key on a mutating tool
resortflow.dining.hold_table -d '{...no idempotency_key...}'   # refused (FR-015)

# Read tool never needs one
resortflow.dining.list_venues   # succeeds with no idempotency_key argument at all
```

## Scenario 6 — a sick vendor degrades alone (SC-010, SC-015)

```bash
# Force dining-sim to fail repeatedly past the breaker threshold
for i in $(seq 1 6); do curl -H "X-Sim-Fault: error_500" ... resortflow.dining.check_availability; done

# Breaker should now be OPEN for dining specifically
resortflow.dining.check_availability   # fails immediately, typed error, no wait on the upstream
resortflow.stay.search_rooms           # succeeds normally — protection is per-vendor

# A commit call whose retries exhaust while OPEN
resortflow.dining.confirm_reservation  # classifies REQUIRES_HUMAN, not RETRYABLE (FR-032)
```

Wait 30s (the cooldown); dining calls should resume succeeding with no operator action.

## Scenario 7 — every call is traced (SC-012, SC-013)

Point the gateway's console exporter (research.md D7) at stdout and invoke any tool; confirm
exactly one span is emitted, every attribute name is one of `observability/attributes.py`'s
constants (grep the emitted output for any attribute name literal not in that module — none
should exist), and a failed call's span `trace_id` matches the `trace_id` on its returned
`NormalizedFailure`.
