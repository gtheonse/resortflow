# Data Model: Prompt Management (Feature 009)

Field lists use plain types; concrete Python/pydantic shapes are decided in tasks. All hashes are
lowercase hex SHA-256 per research R-05.

## PromptTemplate (`prompts/templates/<id>.yaml`)

| Field | Type | Rules |
|---|---|---|
| `id` | string | `snake_case`, unique, no `/`; equals the filename stem |
| `family` | enum | `dining` \| `eval_retrieval_judge` \| `eval_trajectory_judge` |
| `type` | const | `chat` |
| `messages` | list of `{role, content}` | roles `system`/`user`; content contains `{{var}}` placeholders |
| `config` | object | allowed keys only: `temperature` (number), `response_format` (`{type: json_object}`); anything else → reject (S-1). |
| `resolution` | enum | `label` \| `exact` |
| `owner` | string | key into `owners.yaml`; drives CODEOWNERS generation (FR-036/038) |
| `variables` | object | `runtime: [names]`, `tenant: [TenantProfile field names]` — **`required` is not here**: required (code-injected) vars are declared at the call site (FR-007) |

**Validation:** every placeholder ∈ declared set of its call site; no literal `DietaryRestriction`
/ `DietarySeverity` value (lint, FR-028e); no tenant identifier or regulator name (FR-012d);
`resolution: exact` only for judge families; not on the revocation list.

## ResolvedPrompt (runtime value)

| Field | Type | Notes |
|---|---|---|
| `id` | string | template id |
| `version` | string | registry integer as text, or `git-<12 hex>` for Git-sourced |
| `sha256` | string | canonical hash of what is actually served |
| `source` | enum | `git`, `langfuse`, `git-fallback`, `git-fallback-unapproved`, `git-fallback-revoked` |
| `messages` | list | compiled (variables rendered) |
| `config` | object | validated allow-listed keys |
| `rejected_reason` | enum \| null | see research R-07 |
| `registry_version` | int \| null | present only for source `langfuse`; rendered as the `resortflow.prompt.version` string |

## TenantProfile (closed, code-owned)

| Field | Type | Rules |
|---|---|---|
| `tenant_id` | enum `MGV`\|`MHB` | from the **token claim**, never model output |
| `display_name` | string | bounded length (≤ 64), validated charset, no newlines |
| `venue_names` | list of string | each ≤ 64, list ≤ 12 |

No free-text fields. Adding a field requires a code change plus the per-template contract test
(FR-012c). **Today no in-scope template uses any tenant variable**; the contract test asserts the
tenant-variable set is empty per template, so the first addition is a reviewed, visible change.

## Prompt Lock (`prompts/prompts.lock.json`) — append-only

```
{ "schema": 1,
  "prompts": { "<id>": { "approved": [ {"sha256", "added": "<date>", "commit": "<sha>"} ] } } }
```

Invariants: research R-12 (1)–(3) and L2b (a hash may be added only with its template). Never shrinks; regenerated by `prompts.sync lock`.

## Revocation Tombstone (`prompts/revocations.json`) — append-only

| Field | Type | Rules |
|---|---|---|
| `sha256` | string | |
| `prompt_id` | string | |
| `reason` | string | required |
| `date` | date | required |
| `ref` | url/string | incident or PR link, required |
| `break_glass` | bool | true ⇒ merged on incident-responder-group (or compliance) approval + incident label |

## Registry Prompt Version (Langfuse side)

`{name, version:int, type:'chat', prompt:[{role,content}], labels[], tags[], config, commit_message}`.
`push` creates a version only when the canonical hash differs from the registry's latest, labels it
`staging`, and writes an informational `commit_message` (`resortflow-sync <sha256[:12]>`). Nothing is
stored in `config` beyond what the template authors, so a registry version's hash is computable from
its own fields. A version created in the registry UI is scratch: the application never serves it unless its hash is
locked, and nothing imports it into Git (import deferred, ADR-052 D9).

## Owner Group (`prompts/owners.yaml`)

`{group_key: {team_slug, members: [≥2 names], scope: compliance | eval_track | incident}}`.
`codeowners.py` generates the marked block in `.github/CODEOWNERS` in **last-match-wins** order
(FR-042): first `/prompts/ -> compliance` (default: any file added later is owned), then the specific
rules — `/prompts/templates/eval_*.yaml` and `/eval/data/baseline.json` -> eval_track;
`/agents/dining/tests/test_dietary_*.py` -> compliance; `/prompts/revocations.json` -> compliance **or**
incident; `/eval/data/intent_cases.yaml` -> compliance **or** eval_track; each template's `owner` ->
that group's `team_slug`. CODEOWNERS grants approval to any one listed owner (OR), so no rule promises
dual approval. `incident` here is an owner group (incident responders); the `incident` PR label is a
separate CI marker (invariant L6).

## Dietary Enum Snapshot (`prompts/snapshots/dietary_enums.json`) — compliance-owned

`{"DietaryRestriction": [<member values, in definition order>], "DietarySeverity": [...]}`. A contract
test compares the live enumerations in `graph/models.py` with this file; any difference fails CI,
and updating the snapshot needs the compliance owner's approval (FR-037). Order is significant so a
re-ranking is also a visible change. The enumerations themselves are not moved or modified.

## Lifecycle of a prompt version

```
authored (Git)  ──push──►  staged (registry label staging; hash may be unlocked)
      │                           │ eval gate PASS (merge queue) + merged to main
      ▼                           ▼
 locked (hash ∈ approved) ──promote──► live (label production)
      ▲                           │ rollback = move label to earlier approved, non-revoked version
      │                           ▼
 approved-history            revoked (tombstone) — terminal; refused everywhere; never deleted
```

A registry version whose hash was never locked can exist in the registry but is never served by the
application; it can reach production only by an engineer transcribing it into a template -> PR -> gate ->
merge.
